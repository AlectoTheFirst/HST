# Demo enterprise: the synthetic Norlund estate

Three complete fixtures of one fictional company, Norlund, at three points in
time. They are generated by `tools/gen_demo_enterprise.py`; do not edit them by
hand. Every name, serial, address and policy is invented. Addressing uses RFC
1918 space and the IPv4 documentation ranges, and the Oslo office adds IPv6 from
2001:db8::/32 and fd00::/8. The estate is not a capture, an export or a scrubbed
copy of any real network.

The fixtures hold routes with next hops, connected prefixes, PBR redirects and a
load-balancer model. A trace runs through offices, SD-WAN overlays, the ACI fabrics
and the firewall clusters.

## Files

| `estate-v3.yaml` | v2 minus the Milan office (mil01) and the retired Intranet port-80 VIP, plus Azure West Europe. 3,091 nodes. |

A site that exists before the load keeps its parameters. Only an edit on the Sites page

## Load

Load the three versions as three runs. Each `--new-run` load publishes one
snapshot, so the What-changed page can compare any two.

```sh
hst load-fixture --new-run fixtures/demo-enterprise/estate-v1.yaml
hst load-fixture --new-run fixtures/demo-enterprise/estate-v2.yaml
hst load-fixture --new-run fixtures/demo-enterprise/estate-v3.yaml
```

Each load also writes the Hyperspatial Twin map tables of its run. The three
runs form one map timeline, so the map can step from v1 to v3.

`hst load-fixture --dry-run <file>` validates a file without a load.

Import the applications on the Business Applications page with Import, one
file at a time, or through the API: `POST /api/business-applications/import/preview`
with `{"yaml": "<file content>"}` and then `POST /api/business-applications/import/commit`
with the digests the preview returns. After the import, resolve each application
against the current snapshot.

## A demo instance

Set the chart value `demo.fixtures=/usr/share/hst/demo-enterprise` (the app and
the worker read it as `HST_DEMO_FIXTURES`). The Runs page then shows a Demo
estate card to an admin, and Load demo estate starts a `demo` run: it creates the
sites of `sites.yaml` that do not exist, loads the three versions as three runs
with their map tables, under the cycle lock as a collection run, and imports the
five applications and resolves them at the last run. A second load publishes
three new runs and leaves the sites and the application revisions as they are.
The run is listed in the run history.

By hand, without the chart value:

The image holds this folder at `/usr/share/hst/demo-enterprise`. On a fresh
instance, load the three versions inside the app pod, then create the sites and
import the applications through the API. `sites.yaml` gives each site its name,
location and map position, so the Map page lists the sites and the twin map
groups them by country.

```sh
for v in 1 2 3; do
  kubectl -n <namespace> exec deploy/<release>-hst -- \
    hst load-fixture --new-run /usr/share/hst/demo-enterprise/estate-v$v.yaml
done
HST_PASSWORD=... python3 tools/seed_demo.py --base https://<instance host> --user <admin user>
```

The script leaves an existing site as it is, so a second run changes nothing.

## Regenerate

```sh
python3 tools/gen_demo_enterprise.py          # rewrites all files in this folder
python3 tools/gen_demo_enterprise.py --diff   # also prints the node uids added and removed between versions
```

The generator is deterministic. A rerun without a code change produces
byte-identical files. It imports the VyOS collector from this tree's `src/`, so
run it with the project's environment (`uv run python3 tools/gen_demo_enterprise.py`).
A change to the collector's output for the Oslo payload changes the Oslo office
in all three files.
